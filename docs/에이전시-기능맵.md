# 랜덤박스 에이전시 기능 설계

## 제작팀 역할

| 역할 | 책임 | 산출물 |
|---|---|---|
| 총괄 기획·통합 | 요구사항, 사용자·관리자 연결, 최종 검수 | 통합 프로토타입 및 검수 결과 |
| 정책·서비스 기획 | 경쟁서비스 비교, 환불·충전·배송 설계 | 경쟁서비스 정책 조사, 기능맵 |
| 사용자 경험·프론트엔드 | 가입·로그인·충전·결제·개봉·상품 처리 | 사용자 시연 화면 |
| 운영도구·프론트엔드 | 상품·박스·확률·회원·거래·정책 관리 | 관리자 시연 화면 |

미팅에서는 빈 입력으로도 가입·로그인·결제를 완료할 수 있어야 합니다. 실제 인증 또는 결제수단 조회는 하지 않으며, 임시 회원과 거래를 브라우저에 생성합니다. 관리자가 바꾼 가격·확률·충전상품·수수료는 같은 브라우저의 사용자 화면에 반영하는 것이 핵심입니다.

## 연결 흐름의 합격 기준

1. 가입 버튼은 빈 입력에서도 동작하며 생성 회원을 관리자에서 확인할 수 있어야 합니다.
2. 충전 완료 시 충전내역과 회원 잔액이 함께 증가해야 합니다. 결제 완료만 표시하고 잔액이 그대로 남는 방식은 불충분합니다.
3. 박스 구매 시 잔액 또는 데모 결제기록이 반영되고, 개봉 결과가 인벤토리와 관리자 개봉내역에 남아야 합니다.
4. 포인트 전환과 환불을 같은 상품에 중복 적용할 수 없어야 합니다. 신청 상태인 상품은 다른 처리로 이동하지 않도록 합니다.
5. 환불 신청은 기준금액·수수료·실제 반환액을 보여주고, 관리자 승인·반려 결과를 사용자 화면에서 확인할 수 있어야 합니다.
6. 관리자의 가격·확률 변경은 사용자 상세에 반영되어야 합니다. 확률 합계가 100%가 아니거나 음수인 경우 저장을 막아야 합니다.
7. 승인 버튼을 여러 번 눌러도 잔액이 반복 증가하지 않아야 합니다.
8. 새로고침 후 상태가 유지되고, 데모 초기화 시 안정적으로 초기값으로 돌아가야 합니다.
9. 좁은 화면에서도 가입·결제·환불의 마지막 버튼까지 접근 가능해야 합니다.
10. GitHub 공유용 소스에는 실제 계정 비밀번호·결제키·개인 회원 데이터가 없어야 합니다.

## 미팅 진행 순서

비회원 시작 → 입력 없이 가입 → 충전 → 박스 확률 확인 → 결제 → 개봉 → 인벤토리 확인 → 포인트 전환 또는 환불 신청 → 관리자 환불 승인 → 사용자 잔액 확인 → 관리자 가격대별 확률 변경 → 사용자 확률표 재확인 순서로 진행합니다.

외부 시스템 연동과 운영용 보안 구현은 이번 시연 범위에 포함하지 않습니다. 브라우저 저장은 같은 환경에서의 시연 유지 용도이며, 다른 기기와 공유되는 중앙 데이터베이스가 아닙니다.
