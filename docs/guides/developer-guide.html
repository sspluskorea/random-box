1. 인계 범위와 실행

현재 산출물은 React 기반 브라우저 저장형 서비스 화면입니다. 사용자와 관리자 흐름을 검토하기 위한 구현이며 실제 DB·서버 인증·PG·계좌 송금·택배·문자·예약 작업은 미연동입니다. 공개 관리자 주소는 실제 운영 권한 통제를 제공하지 않습니다.

Node.js 22.12 이상을 사용합니다. 의존성은 잠금파일 기준으로 설치하고 Vite 7.3.7을 유지합니다. source-map-js 1.2.2 패치와 pnpm audit 0건을 확인한 의존성 구성이며, 이 결과는 운영 보안 완료를 뜻하지 않습니다.

  1. 잠금파일을 보존하고 의존성을 설치합니다.
  2. 개발 서버에서 사용자 #home과 관리자 #admin을 확인합니다.
  3. node --test tests/*.test.mjs로 회귀를 실행하고 scripts/run-meeting-harness.mjs로 시나리오를 확인합니다.
  4. 빌드 후 배포 산출물의 사용자·관리자·가이드 주소를 각각 확인합니다.

최종 기능 검증 기준은 회귀 191건과 하네스 32건 통과, 빌드 및 React SSR 검사 통과입니다. 실제 서버·PG·송금 검증 결과로 확대 해석하지 않습니다. 기존 박스 등급 디자인과 개봉 애니메이션은 이번 사업 구조 변경에서 수정하지 않았습니다.

wallet.paid는 환전 가능한 페이, wallet.bonus는 환전 불가 포인트입니다. legacy wallet.cash는 1회 bonus로 이관 후 0이 됩니다. 상태 키를 현재 UI 명칭과 동일한 문자열로 바꾸지 않고 의미를 명확히 유지합니다.

payWithdrawals, inventory, conversions, ledger, openings, orders는 회원 ID와 거래 ID로 연결합니다. 화면 필터만으로 서버 권한을 대신하지 않습니다. 실제 개발에서는 회원별 접근 통제를 데이터 조회와 변경 경로 모두에 적용해야 합니다.

3. 페이와 포인트 거래 계약

구매 method는 wallet입니다. 포인트부터 차감하고 부족분을 페이에서 차감합니다. 신규 method cash는 허용하지 않습니다. 유료 충전은 페이, 충전 보너스와 이벤트 지급은 포인트로 구분합니다.

액션처리
REQUEST_PAY_WITHDRAWALamount와 requestId를 받습니다. 잔액 확인 후 페이를 예약 차감하고 신청 기록을 생성합니다.
CANCEL_PAY_WITHDRAWAL본인의 신청 상태만 취소하고 예약 페이를 한 번 반환합니다.
APPROVE_PAY_WITHDRAWAL사유를 기록해 승인합니다. 이미 예약했으므로 추가 차감하지 않습니다.
REJECT_PAY_WITHDRAWAL사유를 기록하고 예약 페이를 반환합니다.
CASH_CONVERT 또는 REFUND호환 액션이지만 신규 결과는 상품 포기 포인트 반환입니다. 현금·캐시 지급으로 표시하지 않습니다.

환전 상태는 신청·승인·거절·취소입니다. createdAt, processedAt, reason, memberId, amount와 요청 식별자를 기록합니다. 실제 송금 API와 정산대사는 아직 없으므로 승인 상태를 은행 처리 결과로 취급하면 안 됩니다.

금액은 안전한 정수로 검증합니다. 중복 요청·승인·취소는 중복 차감이나 반환을 만들지 않아야 합니다. 실제 서버에서는 원장·잔액·거래 상태를 하나의 원자적 트랜잭션으로 처리하고 PG·송금 웹훅 재전송을 멱등 처리해야 합니다.

4. 상품 반환과 기존 데이터 이전

platform.settings.pointReturnPercent 기본값은 60이며 관리자 변경이 가능합니다. product.returnPointPercent가 비어 있지 않으면 상품별 비율을 우선합니다. 0을 미입력으로 처리하지 않고 null 또는 빈 값과 구분합니다.

당첨 시 returnBaseValueSnapshot, returnPointPercentSnapshot, returnPointsSnapshot을 저장합니다. 포인트는 floor(기준가격×비율/100)입니다. 이후 상품 기준가나 반환율 변경으로 보관 상품의 확정액을 다시 계산하지 않습니다.

과거 cashAmountSnapshot이 있는 상품은 동일 금액을 반환 포인트로 이관하고 legacyCapturedAmount=true로 남깁니다. 이 상품은 기존 확정 반환액으로 안내하며 현재 비율 산식을 새로 적용하지 않습니다. 과거 캐시 잔액도 1회 포인트로 합산하며 이관 버전으로 중복 합산을 막습니다.

전환 기록에는 당첨 상품·기준가·비율·지급액·원장 연결과 restorableUntil을 저장합니다. 복구 시 당시 허용 기한과 회수 가능한 포인트를 확인합니다. 제안 대기·배송 신청·기한 만료 상품 등 부적합 상태에서는 직접 반환을 제한합니다.

PROCESS_DUE는 기한과 알림을 확인하는 브라우저 실행입니다. 서버 예약 작업이 아닙니다. 실제 운영 시 서버 시각과 작업 재시도, 중복 실행 방지, 예약 재고 정리, 알림 발송 결과를 별도로 구현해야 합니다.

5. 개봉 게이지와 확률 계산

platform.openingGaugeRules는 A~E별 enabled, startAfterOpenings, gainPerOpening, boostPercent, boostUses를 갖습니다. openingGauges는 회원별 totalOpenings와 등급별 gauge, remainingUses 및 준비 당시 강화값을 저장합니다. 기존 openings를 새 totalOpenings로 소급 집계하지 않습니다.

recordOpeningGauge는 개봉 전 totalOpenings가 시작 기준 이상이고 당첨 등급이 적립 대상일 때 해당 등급만 증가시킵니다. 100% 도달 시 준비 횟수와 강화값을 저장합니다. 이 개봉에는 새 강화가 적용되지 않고 다음 개봉부터 적용됩니다.

openingGaugePlan은 A→E 우선순위 또는 지정 gaugeGrade에 따라 적용 가능한 한 등급을 고릅니다. 해당 등급 합계를 base라 하면 boosted=min(100,base+boostPercent)입니다. 해당 등급 상품은 기존 내부 비율로 boosted를 나누고 다른 상품은 기존 비율에 (100-boosted)/(100-base)를 곱합니다.

대상 등급 상품이 없거나 base가 0 또는 100이면 적용하지 않고 준비 횟수를 보존합니다. 실제 적용 등급만 횟수를 차감하며 모두 소진하면 그 등급만 초기화합니다. 다른 준비 등급은 유지됩니다.

현재 초기값은 A·B 활성, 시작 10회, 증가 20%, 강화 +5%p, 1회입니다. 시연 기본값이며 운영 확정값이 아닙니다. 이미 준비된 강화는 저장된 값으로 처리하고 이후 적립은 변경 규칙을 적용합니다.

6. 추첨 기록과 이벤트

effectiveProductOdds는 박스 구성에 버닝 효과와 현재 게이지를 반영합니다. 구매 다중 수량은 각 개봉마다 재고·게이지·확률을 다시 계산해야 합니다. 첫 번째 확률표를 전체 결과에 재사용하면 안 됩니다.

openings에는 probabilitySnapshot, baseProbabilitySnapshot, appliedGaugeGrade, gaugeBeforePercent, gaugeAfterPercent, gaugeSnapshot을 저장합니다. 당첨 상품 ID, orderId, inventoryId와 회원 ID를 연결합니다. 사용자 상세에서는 해당 회차의 최종 확률표와 적용 전후 등급 확률을 보여줍니다.

박스의 양수 확률 상품에는 유효한 판매 상태와 재고가 필요합니다. 상품 중복과 100% 합계를 검증하고 재고 소진 시 임의 다른 상품으로 확률을 바꿔 지급하지 않습니다. 실제 서버 추첨에서는 암호학적 난수와 변경 불가 기록, 재고 잠금이 별도로 필요합니다.

가입·출석·추천·누적 결제 이벤트는 개봉 게이지와 독립입니다. 이벤트 회차·기간·지급 횟수·재고·중복 지급을 검증하며 지급 포인트는 환전 불가입니다. 이전 CLAIM_PITY 신규 지급은 차단하고 pityClaims와 과거 정정·정산 기록은 읽기용으로 보존합니다.

7. 배송 대체와 개인정보 동의

OFFER_SUBSTITUTION은 보관 상품에 대체 상품과 사유를 제안합니다. RESPOND_SUBSTITUTION은 본인 제안에 수락·거절을 기록합니다. 제안 시 재고 예약, 응답·만료 시 예약 확정 또는 반환이 한 번만 발생해야 합니다.

수락 후 실제 배송명은 대체 상품으로 표시하지만 원당첨 상품·확률·기준가격·반환액은 보존합니다. 제안 대기 중 배송·전환을 차단하며 만료 처리와 직접 사용자 응답이 경합해도 상품과 재고가 중복 변경되면 안 됩니다.

state.settings.security.strictConsents는 기본 false입니다. true이면 가입 consentService/consentPrivacy/consentAge, 충전 consents.payment, 구매 consents.probability/rewards, 배송 address.deliveryConsent, 환전 consents.withdrawal을 검증합니다.

thirdParty 설정은 enabled, recipient, purpose, items, retention으로 구성합니다. 활성 시 배송 단계에서 업체·목적·항목·기간과 동의를 표시하고 thirdPartyConsentSnapshot을 주문에 저장합니다. 외부 전송과 수탁/제3자 제공 법적 분류는 실제 계약에 맞춰 별도 확정해야 합니다.

정책 기본본문 4.0은 페이·포인트와 개봉 게이지 구조를 설명합니다. 알려진 이전 기본본문과 완전히 일치하는 경우만 이전하고 운영자 편집본문·과거 거래 스냅샷은 보존합니다.

8. 관리자 화면과 접근성 검수

관리자 메뉴는 24개입니다. 회원·상품·재무·콘텐츠의 실제 메뉴명과 업무 위치는 서비스 이용 가이드의 관리자 메뉴 표를 기준으로 확인합니다. 목록은 필수 열만 보여주고 상세보기는 해당 행 아래에서 펼칩니다.

  1. 상품 당첨내역·판매내역이 상품 ID 필터로 연결되고 필터 칩 해제·메뉴 변경 초기화가 동작하는지 확인합니다.
  2. 천장 게이지 네 탭의 현재 회원값·설정·강화 기록·이전 기록을 구분합니다.
  3. 환전 승인 사유, 잔액 종류와 조정 사유, 상품 반환율 0%, 쿠폰 상태·기간 오류를 확인합니다.
  4. 1366×768, 1280×720, 1024×768 및 모바일에서 표 내부 가로 스크롤과 모달 내부 세로 스크롤을 확인합니다.
  5. 키보드로 입력·상세보기·저장·닫기에 접근하고 긴 오류 문구·상품명·이미지가 가려지지 않는지 확인합니다.

업로드는 파일 서명·형식·크기 검증을 적용합니다. 외부 링크 허용 범위, CSV 수식 입력 방어, 비정상 중첩 상태, 저장 실패와 오래된 탭 상태를 확인합니다. 현재 검증은 클라이언트 수준이며 서버 파일 검사와 권한 검증을 대체하지 않습니다.

9. 검수 시나리오와 실서비스 개발

  1. 충전 후 페이와 추가 포인트 분리, 포인트 우선 구매 차감, 취소 시 비례 보너스 회수를 확인합니다.
  2. 상품별 반환율 우선·기본값·0%·과거 고정액·당시 스냅샷·복구 기한을 확인합니다.
  3. 환전 신청 예약 차감, 승인 추가 차감 없음, 거절·취소 한 번 반환, 타회원 및 중복 요청 거절을 확인합니다.
  4. 게이지 시작 전후, 당첨 등급만 적립, 100% 다음 개봉 적용, A→E 한 등급, %p 계산, 후보 없음 보존, 다중 개봉별 스냅샷을 확인합니다.
  5. 대체 제안 수락·거절·만료·재고 반환과 원거래 보존, 필수 동의 및 정책4.0 이전을 확인합니다.
  6. 사용자와 관리자에서 동일 거래 ID의 잔액·상태·이력을 비교합니다.

현 검수 결과는 회귀 191/191, 하네스 32/32, 빌드·React SSR 통과입니다. 실제 서비스 전에는 서버 권한·인증, DB 트랜잭션, PG/송금 대사, 개인정보 처리 계약, 서버 예약 작업, 운영자 감사 로그와 장애 복구를 구현하고 통합 검수해야 합니다.

개발 순서는 정책·금융 구조 확정, 서버 데이터와 원장 설계, 인증·권한, 결제·송금 연동, 추첨·재고·예약 작업, 운영 도구와 알림, 부하·보안·정산 검수 순으로 권장합니다. 비용과 납기는 PG·송금 제공사 및 법률 검토, 운영 범위를 확정한 뒤 산정합니다. 이 문서는 견적이나 실제 서비스 적법성의 확정 의견이 아닙니다.

모두의박스 · 서비스 화면과 함께 확인하는 안내서
